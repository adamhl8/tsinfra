# AGENTS.md

tsinfra's design lives in the docs: `docs/README.md` (the design notes), `docs/steps.md`, `docs/cli.md`, `docs/transport.md`, `docs/needs.md`, `docs/recipes.md`, `docs/integrations.md`, and `docs/roadmap.md`. Read the doc for the area you're working on. This file holds only what the docs and the code don't make obvious.

## Working with the user

- Give the user a rundown of the next piece and get their go-ahead before building it.
- Larger work is split into pieces, each reviewed before the next. When the user asks for work in pieces, split it like this:
  - **A piece is one commit,** numbered 1, 2, 3, and so on. It passes lint and tests, and makes sense as a commit.
  - **A sub-piece is one review,** numbered 1a, 1b, then 2a, 2b, etc. It's a smaller diff that's easy to review, and it doesn't have to pass lint until its piece is done.
  - **The feature as a whole comes first.** Order the pieces so nothing one builds is undone or reworked by a later one. Never build something a worse way just so a piece stands on its own. When a split would force that, change the split.

## Checks

- `bunx bask test --all`, for changes to transports, sudo, or file and link writes. The `*.docker.ts` tests run on Alpine (busybox) and Debian (dash), with real root and real `sudo`. Neither `bun test` nor `bask lint` runs them.
- A CLI test can change its project's installed tsinfra, with `replaceInstalledFile` or `removeInstalledFile`, because `createProject` gives each project its own copy. A test never edits a dependency, because every project's tsinfra links to one shared install of them. Another project's `node_modules/.bin/tsinfra` (`getInstalledBin`) stands in for a global copy.
- A CLI test runs tsinfra through `createProject`'s `run` or its `env`, never with `minimalEnv()` alone. Their `HOME` is a temp dir of the project's own, because the test preload's home mock doesn't reach a subprocess, and tests in a file run at the same time. With the real `HOME`, an `apply` and a `plan` on hosts with the same name share one saved state file, and the `plan` can read it while the `apply` deletes it.
- Type tests are `*.tst.ts` files that TSTyche runs, after `bun test` in `bask test` and `bask lint`. TSTyche runs on the real Node (``sh`tstyche`.bun(false)``), because TypeScript 7's API reads a Node-only internal of a child process's stdout, so it crashes under bask's default of running `node` bins on Bun. Assert that a type is refused with a `.not` matcher, like `.not.toHaveProperty` or `.not.toBeAssignableFrom`, rather than `@ts-expect-error`, which oxlint can flag on the same line.
- A test of a host this machine isn't, like a Linux one for a platform check, uses `createSessionWithFacts`. A fake `uname` from `createFakeToolSession` can't stand in, because preparation reads the facts on the transport before the fake tools go on `PATH`. A CLI test can put a fake `uname` on `PATH`, because tsinfra's subprocess gets the `env` the test runs it with.
- Bun's `toMatchObject` takes any two `Set`s as matching, whatever they hold. Compare a `Set` with `toStrictEqual`, on its own or inside a value that has no other fields to leave out.
- A test that presses Ctrl-C during a command waits for the command to show it's running, like the pid file `hosts-interrupt` writes. The progress line names a step before its command starts, and a signal before then ends tsinfra without reaching any command.
- A test that sends content near the 10 MB limit through the local `sh` needs `CONTENT_LIMIT_TIMEOUT_MS`. macOS `/bin/sh` is bash, which reads a script on a pipe one byte at a time, so 10 MB takes about 2.5 seconds of the default 5 second timeout.

## Docs

The docs describe tsinfra as it is. Everything not built lives in `docs/roadmap.md`.

- Markdown is never hand-wrapped. Each paragraph, list item, and blockquote is one line, and line breaks only separate blocks.
- A new design for an unbuilt feature goes in the roadmap, not in the doc it will later belong to.
- When a piece is built, move its design out of the roadmap into the current-state doc and delete the roadmap entry.
- Other docs link to roadmap anchors for gaps.
- Docs never name the maintainer's own setup, like a personal repo, path, or username, because outside users read them. Example users and home directories are `alice` and `/home/alice`.

## Vocabulary

Check new names, comments, docs, and error messages against these words.

- **Host** is the machine a script configures, in code and prose ("runs on the host", `HostFile` for the file found at a path).
- **Target** is only the connection address in `host({ name, target }, fn)` (like `@local`, `sonarr.lan`) and a symlink's target in `h.link`.
- **Host script** is a file in `hosts/` (`HostScript`, `HOST_SCRIPT_EXTENSION`, the `hostScript` name kind), never "host file".
- **Change** is anything that modifies the host (the summary's `N changes`). **Drift** is a change a step that reads the host found (a `changed` status), or a run that only changes still open from an earlier apply triggered (a `ranFromOpenChanges` status). Those are the only things that make `plan` exit 2. **Run** is a change with no drift behind it. Don't coin a word for non-drift changes.
- **Read step** is a step that tells the script about the host (`read`, `inspect`). **Change step** is a step that can change the host, whether or not it does (`file`, `ensure`, `run`, `link`, `dir`, later `reboot`).
- **Tools** are named for what they can do, not which step has them. A check function gets `ReadTools`, even though `ensure` is a change step, and a fix or run function gets `ChangeTools`.
- **Meta** is what `h` holds besides its steps, known before the script runs (`h.meta`, `HostMeta`), like the host's name and sudo password. A value goes in it only when it's about the host and isn't a step.
- **Fact** is only something read from the host, like the CPU architecture. `h.facts` (`HostFacts`) holds the ones preparation reads. What a report shows under a step is its **details**.
- **State** appears only in prose, for the host's version of something, not in identifiers (`compareFile`, not `compareFileState`). The "state command" is the exception, because it's a documented term.
- **Saved state** is what tsinfra itself keeps on a host between applies (`~/.tsinfra/state/<host>.json`, the `saved-state` package), in code and prose, so it never reads as the host's state. Inside that package, plain `state` in a local name is fine where the context is clear. **Open changes** are the first part of saved state. A step that's right, but whose change is still open from an earlier apply, is **`resume`**.
- **Follow-up** is a step whose `after` names the steps it follows, today a `run` and later a `reboot`. Use it, not "run", in code that would apply to any of them, like `recordFollowUp(followUpName, stepNames)`.
- **Integration** is a set of functions that take `h` and call steps to set up one specific program, service, or piece of config, like apt packages or systemd units (see the roadmap's Integrations worth shipping), never "helper", "module", or "provider". A function a script writes for itself, without that scope, can still be a helper.
- **Preparation** is what runs before a host's script, never "preflight" or "host failure".
- **Session** is one host's run of its script, after preparation. `createHostSession` builds `h` for it, and the session recorder records it. What preparation gives it is its **setup** (`SessionSetup`). What every step of it shares is the **session context** (`SessionContext`, `ctx.session`), beside the **step context** built for each step (`StepContext`, `ctx.step`). A handler and its parts take the whole `HandlerContext` and read what they use.
- **"Outcome"** isn't a term in the code.
- **Status line** is a report entry's line (`StatusLine`). The CLI's transient line on stderr, like `Planning host 'sonarr'...`, is the **progress line**.
- **"Note"** is the report's word. A **host note** is about the whole host and shows once, before its entries (`HostNote`). An entry's note follows its name (`NotePart`). **"Diff"** means the line output in the report, so it doesn't name a comparison.
- **Message** is what `h.log` records, never a "log line" or a "note". A **host message** is one logged in the host function outside any step, an entry of its own (`HostMessageRecord`, `HostMessageEntry`, `kind: "hostMessage"`), the way a `host fn` failure belongs to the host and not a step. A **step message** is one a step's function logged, data on that step (`StepMessageRecord`, `StepMessage`, in the `kind: "stepMessages"` detail). Plain "message" names only what both share, like `MessageKind`, `recordMessage`, and `MESSAGE_LEVELS`. Its kind, `info` or `warn`, is `messageKind` (`MessageKind`) for both, never `level`, because a level is the verbosity a piece shows from, and never plain `kind`, which tells a host message apart from a step. A step warning is tsinfra's own, worked out from the facts, so it isn't a message, even though both show as `warning:`. A **host warning** is tsinfra's own too, about the whole host (`HostWarningRecord`, `HostRecord.warnings`, `HostWarning`). It's never an entry, because entries are in script order and preparation records it before the script runs. The report's own asides, like notes and hints, are in `report/format/elements/asides.ts`, so that file's name never reads as being about messages.
- **"Owner"** stays the plain word for the concept and for the chmod permission class. The option is `user`, to pair with `group` and match `stat` and `chown user:group`. `FileOwner` is the type both take.
- **A `want`'s kinds** are boolean, string, list, set, and record, in code, comments, docs, and test names (`RecordWant`, "a record `want`"). Never call a record an "object `want`" or a list an "array `want`". A list and a set are different kinds, so neither word stands in for the other. A value inside a record is named by its kind too, like "a nested record", "a nested list", or "a nested set", never a "sub-object", "child object", or "nested array". An error message names the JS type where it says what a value must be, like "an array of strings, a Set of strings, or an object (of strings, numbers, booleans, null, arrays, Sets, or nested objects)", so a reader can match it to their value. Where it talks about a kind, it uses the kind's name, like "a record want needs a check function".

## Naming values from the host

Each name should say which side of a comparison it is. When naming anything in a compare or write function, check whether a reader could mistake it for the wanted value or the host's value.

- A value read from the host that sits next to a wanted value is `current...`: `currentTarget` (what a link points to now), `currentOwner` (who owns the path now). The wanted side keeps the plain input name (`target`, `options.user`).
- `attributes` always means a file's actual attributes (`HostFileAttributeDetails`). The wanted side is always `options`.
- A list of differences is `...Changes`: `attributeChanges`, `ownerChanges`. A single one is `LinkChange`, `ModeChange`, `OwnerChange`.
- Don't prefix a local with `host` just to say it came from the host. Keep `host` when it names the host itself (`hostSession`, `hostReport`), when it matches a type and its producer (`hostFileDetails` from `getHostFileDetails`), or when it's the only thing telling two values apart (`hostContentDetails` next to `resolvedContent`).
- A discriminant read off details gets a name that isn't plain `kind`, because `kind` means the step kind (`linkDetailsKind`).

## Writing

- **Wrappers.** When a comment, JSDoc, doc, or plan describes wrappers (a transport wrapping a transport, a shell around a transport, recorders), say what wraps what ("wraps", "around") or the order a command passes through ("before the root transport wraps it in `sudo sh -s`"). Never say "above" or "below", because readers picture a wrapper stack in either direction.
- **Formatting.** All formatting belongs in the report. That covers recorded values, not error messages. An error message can format what it needs, like `prettyBytes` in the size limit error.

## Layout

- **`src/` holds the CLI (`cli.ts`), the report (`report.ts`), `core/`, and `integrations/`,** plus the published `index.ts` and code the first three share (`mode.ts`, `styles.ts`, `utils.ts`). `core/` holds hosts, the session, the recorder, saved state, and transports, the part of tsinfra that does the work. The recorder and saved state sit beside `hosts/` and `session/`, because preparation and the session both use them. Nothing in `core/` imports the CLI, the report, or an integration.
- **A general helper goes in the `utils.ts` of the part that uses it:** `core/utils.ts`, `report/utils.ts`, `integrations/utils.ts`, or `src/utils.ts` when more than one part does. It goes there even with one caller, and doesn't get a file of its own. `src/utils.ts` imports no packages, because the launcher loads it.

## Architecture

- **Preparation reads every fact in `h.facts`,** with the readers in `FACT_READERS` in `core/hosts/prepare/host-details/facts.ts`. Each fact's reader, in its own module under `facts/`, takes a `FactContext` (`shell`, `recorder`) like a handler takes its context, runs its own command, parses and checks what it printed, returns the value, and records a warning through `ctx.recorder` when it finds one. `readHostFacts` runs them one at a time, so preparation records its commands in the same order on every run. A fact belongs there only when nothing in a run would reasonably change it, it's cheap to read on every host, and many scripts want it. Anything else stays an `h.read` in the script. The facts stay inside host details, because they're a kind of host detail, and because the test preload swaps `facts.home` by wrapping `buildHostDetails`, the one preparation function that gets the `LoadedHost` its temp home is keyed by.
- **A fact's type lists the names tsinfra knows, but the value can be one it doesn't.** A named fact's reader gets its value from `toNamedFact`, which maps a spelling tsinfra knows to its name, like `aarch64` to `arm64` in `facts/system.ts`, and passes anything else through as the host printed it, recording a host warning, so the host still runs. Code that looks a fact up uses `getOwnValue` and handles `undefined`, and a `switch` over one has a `default`, even where TypeScript calls it exhaustive.

- **A comparison records what tsinfra works out, and the report only formats it.** Whether a step is in sync, and what's unmet, missing, or extra, is worked out once, before masking, and the fix and the report read that one result. The report never compares two sides itself, because masking can make two different values look the same. Line diffs are the exception: the report computes them when it renders, because their time and line limits follow its verbosity.
- **Deep comparisons use Remeda's `isDeepEqual`, never Bun's `deepEquals`.** Bun's tells `-0` from `0`, which the report shows as the same `0`, so every comparison uses one equality, whatever it compares.
- **A generic over a step's `want` takes `T extends WantOf<T>`, never `T extends Want`.** `Want`'s record is an index signature, which a type an interface declares can't match. `RecordWantOf` maps each valid value to `unknown`, because a primitive there keeps `want`'s inferred values literal, so `{ a: "1" }` couldn't match a check that returns any string.
- **In `core/`, `session/script-boundary.ts` is the only code that throws.** Everything the script can call (the `h` methods and the tools) is `callOrFail` around a `Result`-returning internal. `h.log` is synchronous, so its methods use `callOrFailSync`. `session.ts` only builds `h` from the parts beside it: the boundary, `callStep`, and `h.log`.
- **What a call has one of is returned, and what it finds zero or more of is recorded where it's found.** A step's status and a failure are what a call returns, and the caller acts on them. Nothing carries a warning, an option, or a message up only so something above can record it.
- **Code records through the recorder on its context, where it finds something,** like a handler calling `ctx.session.recorder.recordOptions` right after validating its options, so a later failure can't lose them. A step's code gets only `StepRecorder`, so it can't start or finish a step, and a fact's reader gets only `HostWarningRecorder`. `HandlerReturn { status, value }` carries only the status `callStep` records and the value the script gets.
- **A check reports the same** whether it's a command string or a function with one `inspect`.
- **`runProcess` doesn't pass `env` to `spawn`,** so a host script's changes to `process.env` never reach the commands tsinfra runs. Bun's `spawn` gives children the environment the process started with, so a test can't move `HOME` either. Instead, the test preload mocks `buildHostDetails` to give each host a temp `home`, ssh ones included, because the only sshds the tests reach run on the same machine as the same user.
- **Paths tsinfra keeps under a host's home come from `core/hosts/prepare/tsinfra-directory.ts`,** built from the checked `HomeDirectory`, never as `"$HOME"` in a script. The test preload's mock swaps `facts.home` on what `buildHostDetails` returns, so it reaches paths built after preparation, like saved state. It doesn't reach the askpass helper, which `buildHostDetails` writes itself, so tests find the helper in the real home.
- **`report-preview.ts` has no test preload,** so it runs its hosts in a child process started with a temp `HOME`. Otherwise each host that fails there leaves its saved state in the real `~/.tsinfra/state/`.
- **`src/cli.ts` is the launcher, so it statically imports only what finding the project's copy, handing off, and parsing need.** It loads the run with `import("#cli/run.ts")`, so a global copy never loads its own core next to the project's. A new import the run needs goes in `cli/run.ts`, not `cli.ts`.
- **The `./cli` and `./package.json` exports never move or change shape,** because an old global copy has to start any newer project copy through them.
- **A failure hint's rule lives in the transport whose tool prints what it matches,** like `getSshFailureHint` in `core/transport/ssh.ts` and `getSudoFailureHint` in `core/transport/sudo.ts`. Each takes the failed commands' text and only the parts of the host it needs, and returns its hint or `undefined`. `FAILURE_HINT_RULES` in `core/recorder/failure-hints.ts` lists every rule, and the recorder runs them all when a host fails. A hint reads the recorded commands, not the failure's error, because a failure's error doesn't always come from the command that printed the reason, and a `sudo -n` that needs a password exits 1 without an error.
- **Recorders follow the stages of a run** (preparation, then the session), not the host, step, and converge hierarchy.
- **Only the filter knows the verbosity.** The builder gives every piece the levels it shows at, the filter (`toShownHostBlock`) keeps or drops pieces by them, and the formatter formats whatever is left. Where something shows is a piece too, when it changes with the level, like a step message's `amongCommands`: the filter drops it below 2, and the formatter checks only whether it's there, so it puts the message among the commands or in a row under the step without seeing a level.
- **All recorded text goes through a palette style,** even text left in the terminal's own color (`stylePlain`), because the palette's styles are what mute `[MASKED]`. Text that skips one shows `[MASKED]` in the color around it. The `hosts-masked` CLI test checks that every `[MASKED]` it prints is dim.

### `src/core/session/handlers/`

`handlers/` is the boundary where arguments from the script enter, so the rule is visible from the file tree.

- The top level holds only handlers. Each takes the script's values as `unknown` and validates them, with the public types and schemas for that input next to it: one file per step, and `tools.ts`.
- `handlers/<step>/` holds one handler's own stages, named without the step prefix. A step's own read, comparison, and write stay in its folder.
- `handlers/shared/` holds code more than one handler uses. Its helpers may take `unknown` and validate it, like `validateInput` and `validateHostPath`. It's for building blocks no one step owns.
- A step can build on another step's internals. It imports them from the module that declares them, like `dir` importing `compareRecords` from `ensure/comparison/record.ts`.
- `handlers/shared/filesystem/` holds the filesystem building blocks (paths, sizes, stat commands, write-script pieces, and attributes), even when only one step uses one. `attributes.ts` holds the attribute types and their comparison, and its parts sit in `attributes/`: modes, owners, and the claims that keep two steps from setting one differently.
- `handlers/options/` holds the options interfaces that steps' and tools' options extend, grouped by what the option is about, not by who takes it. `command.ts` holds how a command runs (`sudo`, `env`, `input`, `maskOutput`), `step.ts` what only steps take (`needs`) and the shell options `callStep` handles, and `attributes.ts` a path's owner and mode. Each handler keeps its own options interface and schema, extending these.
- A value a script function returns is validated where it's used, not in `handlers/`'s top level.

### `src/integrations/`

- **An integration is code a host script could have written.** It uses only what `index.ts` exports, and throws like a script, with a message written as a sentence. Inside tsinfra it imports each name from the module that declares it, like `Host` from `core/session.ts`.
- **Each integration's `index.ts` is its export path,** like `integrations/macos/file-handlers/index.ts` for `tsinfra/integrations/macos/file-handlers`. It declares everything the path exports, with its parts beside it in the same folder. `package.json` exports `./integrations/*` from each `index` file, so the parts and shared files like `jxa.ts` stay private, and tsdown builds every `index.ts` under `src/integrations/`. A new integration needs only its `index.ts` and a row in `src/__tests__/exports.test.ts`, which fails until it has one. A fixture that imports it needs it declared in `src/__tests__/fixtures/tsinfra.d.ts`. No code imports another integration's `index.ts`, so a helper two integrations share moves to shared code first.
- **An integration that works on one platform calls `assertPlatform` from `integrations/utils.ts` first,** in each function it exports that touches the host, so a script stops before the integration's first step. It reads `h.facts.platform`, so it runs nothing on the host.
- **Write JXA as typed TypeScript functions, not strings.** `toJxa` in `integrations/macos/jxa.ts` sends `fn.toString()` to `osascript` through `env`, because Bun strips the types on load. Each function must be self-contained, because only its own source reaches `osascript`. Coverage shows these functions as unrun, because they run in `osascript`. `exports.test.ts` runs one from the packed package, because the build's output is what reaches `osascript`.
- **The macOS tests only read and plan,** because applying would change the Mac running them. They're skipped off macOS, because CI runs on Ubuntu.
- **`fileHandlers` sets handlers through the Launch Services API, never by editing its plist.** `lsd` keeps handlers in memory and overwrites `com.apple.launchservices.secure.plist` from that state, so a `defaults write ... LSHandlers` entry it didn't load reads as set until `lsd` next saves, then vanishes. `fileHandlers` calls `LSCopyDefaultRoleHandlerForContentType` and `LSSetDefaultRoleHandlerForContentType` through JXA instead.
- **A handler change only counts once macOS has applied it.** On macOS 27, Launch Services treats every content type tried so far as protected, so a call from `osascript` returns success but only asks `CoreServicesUIAgent` to prompt the user. The agent applies the change after they agree. `fileHandlers` sends every change at once, because macOS groups some into one prompt, then `waitForHandlers` polls until they've all taken effect. The log shows the decision as `_LSCheckEntitlementValueForChangingDefaultHandler: result=NO: scheme or content type is protected`.
- **Only Finder can handle `public.folder`.** Since macOS 26.6.2, Launch Services rejects any other app for it with status `-50`, and the log says `bindable public.folder failed validation`.
- **`fileHandlers` sets only an extension's preferred type,** because that's the type its files get. The other types that list it can be the preferred type of another extension.
- **`readInfoPlist` reads through `NSBundle` in JXA, not `plutil`.** `plutil -extract ... json` refuses a value that isn't an array or a dictionary, like a string.
